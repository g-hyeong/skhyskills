# 솔루션 설계

프로젝트 공통 `.skhy/discovery.md`를 **기본 입력으로 먼저 읽는다.** 요구·제약·용어·데이터 기준·미확인을 재사용하고 최신 사용자 정정과 대조한다. 유효한 공통 `.skhy/design.md`가 있으면 해당 설계를 재사용하며 근본적인 해결 방향·계약 변경이 필요할 때만 관련 결정을 다시 논의한다. 산출물의 유효성·단계 선택은 [공통 인계 기준](../plan-execution/references/records.md)을 따른다.

분석에 업무 목적·판단 기준·필수 결과를 바꾸는 핵심 질문이 남아 있으면 [task-discovery](../task-discovery/SKILL.md)에서 실제 답을 기다린다. 문서가 저장됐어도 답변 전에는 설계를 시작하지 않는다. 파일이 없고 대화에 유효한 분석이 있으면 그 근거를 사용하고, 현재 결정에 영향이 없는 미확인은 그대로 둔다.

[질문 기반 설계](references/design-dialogue.md)에 따라 **업무가 시작되는 지점부터 최종 산출물까지 순서대로 짚고, 각 단계의 중요한 미정 사항을 하나씩 합의한다.** 추천안·대안·다른 의견을 받을 기회를 주고, 답에서 확정된 결과를 다음 단계의 입력으로 삼는다. [승인 기준](../plan-execution/references/approval.md)에 따라 설계 검토를 구현·설치 권한으로 확대하지 않는다.

독립적인 대안 조사·검토의 위임이 유리할 때만 [delegate-work](../delegate-work/SKILL.md)를 보조로 사용하고, 주요 선택과 사용자 조율은 부모가 맡는다.

선택한 작업과 스택에 필요한 참조만 읽는다. 구조 선택에는 [구조](references/architecture.md), 외부 API/AI 연동에는 [API](references/api.md), UI에는 [UI](references/ui.md), 검증 깊이에는 [테스트](references/tests.md), Git 정책에는 [Git](references/git.md)을 사용한다. 파일 이름이 목록에 있다고 전부 읽지 않는다. 기술의 구체적 사용법은 제공 버전과 공식 문서로 확인한다.

합의가 끝나면 [공통 기록 기준](../plan-execution/references/records.md)에 따라 `.skhy/design.md`를 작성·갱신한다. 문서만 읽어도 업무 목적과 단계별 입력·판단·결과가 이어지고 예외·검증 기준과 합의 이유를 알 수 있게 한다. 설계 요청에는 문서 저장이 포함된다. 파일 작성 금지나 저장 장애가 있으면 현재 상태를 알린다.

확정한 설계의 저장과 내용 확인 후 별도 단계인 [개발 정책 반영](references/development-policy.md)을 진행한다. 기존 확정 설계로 후속 작업을 재개할 때도 이미 반영된 정책을 재사용하고 누락·변경된 부분만 반영한다. 검토·질문만 요청하면 의견을 전달하고 파일을 쓰지 않는다. 대상 프로젝트 루트 `AGENTS.md`에 합의한 정책이 반영됐음을 확인한 뒤에만 [plan-execution](../plan-execution/SKILL.md)의 구현 계획 단계에 인계한다. 반영이 막히면 설계 저장 여부와 남은 정책 작업을 구분해 알린다. 완료 응답에는 실제 문서 링크와 꼭 필요한 남은 사항을 담는다. 코드 구현에는 별도 계획 승인이 필요하다.
