# 질문으로 설계 완성하기

프로젝트 공통 `.skhy/discovery.md`의 요구·제약·용어·데이터 기준·남은 질문을 읽고, 과제에서 고정한 조건과 사용자가 이미 확정한 결정을 먼저 분리한다. 기존 유효한 `.skhy/design.md`가 있으면 새 설계를 시작하지 말고 변경할 결정만 다룬다.

## 업무 흐름을 따라 질문하기

- 과제의 흐름에서 누가 어떤 입력을 받아 업무를 시작하는지 짚는다. 첫 미정 단계에서 담당자나 시스템이 무엇을 판단·처리해야 하는지 하나씩 묻는다. 답을 받으면 확정한 결과와 이유를 짧게 정리하고, 그 결과를 누가 어떻게 사용하는지 따라 다음 질문으로 넘어간다. 이미 정해진 단계는 설명으로 연결한다.
- 질문에는 결정할 사안·과제상 이유, 추천안과 이유, 실질적인 대안의 이익/부담을 담는다. 비교가 의미 있으면 후보 2~3개를 제시하되 선택지를 채우려고 부적절한 안을 만들지 않는다. 다른 안·조건 수정·보류도 자유롭게 답할 수 있어야 한다.
- 현재 호스트의 질문 도구를 우선 사용한다. 도구가 없으면 대화로 같은 내용을 묻고 실제 답을 기다린다. 추천안의 기본 선택·무응답은 동의가 아니다. 도구 지원 밖의 필드나 자동 승인을 가정하지 않는다.
- 과제에서 지정한 조건과 동일 범위의 실제 사용자 합의는 재사용하고 재질문하지 않는다. 사용자 대신 미정인 기술·제품 선택을 확정하지 않는다. 추후 구현할 변수명 같은 세부 사항은 지금 설계 결정으로 확대하지 않는다.

예를 들어 재검 기록에서 Lot별 최신 결과를 지정 CSV로 넘기는 과제라면, 분석에서 확인한 행 단위와 최신 판정 기준을 출발점으로 삼는다. 먼저 담당자가 검사 기록을 어떻게 불러올지 정하고, 이어서 판정이 보류된 행을 어디서 검토할지, 마지막에 지정 열에 담긴 결과를 원본과 어떻게 대조할지 합의한다. 최신 판정의 업무상 의미 자체가 불명확하면 설계 선택지로 정하지 말고 분석의 확인 질문으로 되돌린다.

아래 항목은 필요한 설계 결정이 빠졌는지 확인할 때 쓴다. 기술 선택은 해당 업무 단계의 결과나 제약에 영향을 줄 때 다루고, 전체 흐름에 걸친 공통 결정은 관련 단계가 드러난 뒤 함께 정리한다.

| 결정 단위 | 사용자와 확정할 내용 |
| --- | --- |
| 해결 방향과 실익 | 누가 무엇을 판단/행동할지, 대안별 이익·한계, 관찰 가능한 성공 기준; 근거 없는 정량 효과를 만들지 않음 |
| 제품 형태와 기능 범위 | 웹/기타 형태, 핵심 흐름, 필수 기능·선택 기능·제외 범위, 우선순위 |
| 기술 선택 | 제공 환경과 시간에 맞는 스택, 기존 코드 재사용, 필요한 의존성·서비스의 도입 범위 |
| 데이터·API·상위 구조 | 데이터 출처와 계약, 외부 API/AI 역할과 실패 대응, 상위 폴더·모듈 책임 |
| UI와 컴포넌트 | 정보 위계·시각 방향·화면 흐름, 공통/기능 컴포넌트 경계, 반응형 범위와 loading/empty/error/success; UI가 없으면 해당 결정 생략 |
| 테스트와 Git | 검사 깊이·진행 방식, 브랜치/워크트리·논리 단위 커밋·기록 추적과 로컬 Git 계획 버전 관리 |

해결 방향의 후보가 한 기능의 변형으로만 모이면, `.skhy/discovery.md`에서 사용자가 내려야 할 업무 판단과 그 목적을 다시 짚는다. 예를 들어 주어진 시간표에서 겹친 일정을 조정하는 과제라면, 경고 표시를 바꾸는 안만 나열하지 말고 충돌한 일정 쌍을 찾아주는 방식과 옮길 수 있는 빈 시간대를 계산하는 방식의 실익을 비교한다. 과제가 지정했거나 사용자가 확정한 기능·형태와 제출 범위를 지키고, 제공 자료로 가능한 대안 중 실제로 선택이 필요한 부분만 질문한다.

제공 환경·기존 코드·제출 조건·가용 시간을 우선한다. TypeScript·Next.js·React는 후보이며 필수가 아니다. 새 의존성·서비스·비용·권한도 필요한 선택과 함께 확인한다. 테스트 깊이는 핵심 업무 위험에 맞추고 고정 커버리지를 강제하지 않는다. Git 정책은 기존 합의를 우선하며 기본 메시지는 `type: 한국어 제목`, 빈 줄, 한국어 불릿이다. 계획은 최신 확정본 파일 하나와 로컬 Git 이력으로 관리한다.

뒤 단계의 답이 앞선 결정을 바꾸면 영향받는 선택만 다시 논의한다. 과제의 원래 요구나 데이터 의미가 달라지면 task-discovery의 해당 분석을 먼저 갱신한다. 핵심 질문의 답에 의존하는 설계는 답을 받을 때까지 보류한다.

## 산출물 확정

설계 문서를 만들기 전에 질문·검토·피드백으로 필요한 결정을 합의한다. 아직 답을 받지 못한 핵심 선택이 있으면 질문을 이어가며 완성된 설계 파일을 먼저 만들지 않는다. 사용자가 별도로 진행 중 초안 저장을 요청한 경우만 검토 중임을 표시해 기록한다. 기존 확정 설계가 있으면 변경 합의가 완료되기 전까지 기존 파일을 유지한다.

합의가 끝나면 설계 요청의 기본 산출물인 공통 `.skhy/design.md`를 작성·갱신한다. 별도 저장 승인은 요구하지 않는다. 파일 작성 금지가 명시됐거나 실제 저장 장애가 있으면 그 상태를 밝힌다. 이전 확정본은 합의된 로컬 Git 정책으로 추적한다. 작업 ID는 만들지 않으며 질문별 답과 승인 범위를 짧게 연결한다.

문서 첫머리에 누구의 어떤 업무를 해결하며 최종적으로 무엇을 전달하는지 적는다. 본문은 실제 업무 순서로 쓴다. 각 단계의 입력과 출처, 담당자나 시스템의 판단·행동, 생성한 결과와 이를 받는 다음 단계 또는 최종 산출물을 연결한다. 처리할 수 없는 경우의 대응과 결과가 맞는지 확인할 기준은 해당 단계에 붙인다. 프로젝트 공통 구조·기술·검사·Git 정책은 필요한 곳에서 모아도 된다.

문서만 읽는 사람도 중요한 선택에서 무엇이 쟁점이었고 어떤 답과 이유로 결정했는지 알 수 있게 해당 단계에 요약한다. 입력 discovery의 경로·개정과 실제 합의 근거를 연결하고, 필수 요구별 대응 기능·계약과 남은 미확인·미충족을 구분한다. 조합 과정에서 새로운 선택이나 범위가 생기면 먼저 묻는다. 이미 합의한 내용을 정리할 때는 승인을 다시 요구하지 않는다.

저장한 설계에서 업무 시작부터 최종 산출물과 검증까지 따라갈 수 있는지 확인한 후 [개발 정책 반영](development-policy.md) 단계로 넘어간다. 정책 반영과 실행 계획 승인은 각각 별개다.
