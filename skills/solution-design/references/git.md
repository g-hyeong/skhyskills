# Git

```text
feat: 예약 생성 API 추가

- 입력 검증과 예약 처리 책임 분리
- 중복 요청의 오류 응답 추가
- 정상·중복 요청 테스트 통과
```

- `type: 한국어 제목`, 빈 줄, 한국어 상세 불릿 본문을 사용한다. 유형은 feat, fix, refactor, test, docs, chore, perf, build, ci, revert 등을 의미에 맞게 고른다. 구분에 도움이 될 때만 scope를 쓰고 호환성을 깨면 `!` 또는 `BREAKING CHANGE:`로 영향과 전환을 설명한다. 프로젝트의 합의된 규칙을 우선한다.
- 독립 기능·수정 목적마다 개별 커밋한다. 하나의 기능과 필요한 테스트는 함께 묶되 큰 요청 전체를 한 커밋으로 압축하지 않는다. 무관한 포맷·리팩터링은 분리한다.
- 추가할 경로를 명시하고 diff를 검토한다. 원래 있던 변경이나 다른 작업의 staged 변경을 포함하지 않는다. 같은 작업 트리의 Git 쓰기는 한 담당자가 직렬 수행한다.
- 브랜치·워크트리는 최초 정책 합의에 따른다. 검사만을 위한 불필요한 커밋은 만들지 않는다. 커밋 후에도 검증한 내용과 최종 내용의 일치를 확인한다.
- 테스트 실패도 실제 근거로 남긴다. 커밋 메시지에 실행하지 않은 검사를 통과했다고 쓰지 않는다. 과제 중 기록을 꾸미려고 squash·재작성하지 않는다.
- 계획 버전 관리는 로컬 Git을 사용한다. 변경안을 사용자에게 확정받고 이전 확정본이 커밋돼 있는지 확인한 뒤 같은 계획 파일을 갱신·커밋한다. 승인 기록도 확정본과 연결한다. 커밋 메시지에는 바뀐 범위·이유를 적고, 코드와 독립적인 계획 변경은 `docs` 등 의미에 맞는 커밋으로 남긴다.
- 계획 본문의 과거 버전을 복제·누적하지 않는다. 직전 계획은 `<commit>:<path>`로 연결하고 `git show <commit>:<path>` 또는 `git log -p -- <path>`로 조회한다. SHA는 실제 생성된 값만 쓰며 현재 커밋의 SHA를 자기 파일에 넣으려고 추가 커밋하지 않는다. 기록만으로 커밋 권한을 새로 만들지 않는다.
- 응시 환경에서는 Git push와 외부 전송을 하지 않는다. 로컬 Git 기록은 유지한다.
