# 제한 시간 안의 검증

기본은 구현과 테스트 병행이다. 결함 수정은 재현 테스트부터 시작하고, 복잡한 순수 로직은 TDD가 이득인지 판단한다. 설계에서 검사 깊이·방식을 정하고 승인 실행 계획에서 실제 검사·완료 기준으로 구체화한다.

| 대상 | 우선 검사 |
| --- | --- |
| 핵심 계산·도메인 규칙 | 정상·경계·실패 단위 테스트 |
| API·외부 연동 | 입력/응답 계약·타임아웃·원격 실패 |
| 생성형 AI 사용 시 | 핵심 업무 사례의 근거·계산 보존·불확실성·프롬프트 인젝션 대응([API 기준](api.md)) |
| UI | 실제 주요 흐름·오류·빈 상태·입력 |
| 전체 결과 | 타입 검사·빌드·주요 기능 스모크 |

모든 코드를 같은 깊이로 검사하지 않는다. 사용자 영향과 변경 위험으로 선정한다. 실행 명령은 실제 프로젝트의 package scripts와 제공 환경을 확인해 선택한다. 존재하지 않는 스크립트를 관습으로 가정하지 않는다.
필수 검사를 못 돌리면 미실행으로 남긴다. 제한 시간이 부족하면 범위 조정을 제안하고 사용자가 확정한 변경만 적용한다. 검토·검증만 요청받은 작업은 발견 사항을 보고하며 수정 권한으로 확대하지 않는다. 근거 없는 커버리지 목표·전체 로그 반복 첨부는 하지 않는다. 긴 원본 출력은 필요시 해당 작업의 `evidence/`에, 판단·검증 결과는 현재 단계의 작업 파일에 짧게 남긴다. 구체적인 경로와 담당은 [공통 기록 기준](../../plan-execution/references/records.md)을 따른다.

## 원인 불명·간헐 오류의 재현

수정 전에는 허용된 환경에서 사용자가 겪은 증상을 재현할 짧은 동작과 판정값을 정하고 실제 결과를 확인한다. 예를 들어 동시 요청에서 중복 저장이 발생하면 같은 요청을 동시에 보내고 생성된 레코드 수를 센다. 가능한 원인마다 예상 결과를 정한 뒤 한 번에 한 조건을 바꿔 어느 가설과 맞는지 확인한다.

수정 후에는 원래 입력·실행 조건·판정값으로 다시 검사한다. 간헐 오류는 수정 전후 각각 증상 발생 횟수와 전체 시도 횟수를 함께 제시한다. 수정 전 상태를 다시 실행하기 어려우면 같은 조건에서 확보한 기존 근거를 활용한다. 수정 전 증상을 확인할 근거가 없으면 회귀 검증의 한계를 밝히고, 수정 후 0건도 관찰한 횟수와 조건 안에서만 해석한다.
