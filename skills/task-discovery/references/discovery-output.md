# 문제 분석 산출물과 응답

목적은 사용자가 과제를 이해하고 다음 설계에서 근거로 사용할 수 있게 만드는 것이다. 기술 스택·해결안을 이 단계에서 확정하지 않는다. 과제 분석 요청의 기본 결과로 프로젝트 공통 `.skhy/discovery.md` 하나를 작성·갱신한다. 저장 여부를 다시 묻지 않는다. 명시적으로 파일 작성을 금지했거나 실제 저장 장애가 있을 때만 대화로 전달하고 저장하지 못한 상태를 밝힌다.

## 분석 본문

다음 일곱 항목을 기본 순서로 사용한다. 과제 크기에 맞게 짧게 쓰며 해당 없는 내용을 만들거나 모든 용어를 조사하지 않는다.

| 항목 | 담을 내용 |
| --- | --- |
| 1. 문제 요약 | 누구의 어떤 문제인지, 무엇이 해결되면 성공인지 쉬운 말로 설명 |
| 2. 업무 배경과 현재 흐름 | 상황·담당자·정보·판단·행동의 연결과 현재 어려움 |
| 3. 핵심 용어와 관계 | 이해에 필요한 용어, 데이터/업무 개념 사이의 관계와 혼동 지점 |
| 4. 요구사항과 제약 | 필수·선택·금지/제한·제출물·완료 기준을 구분하고 원문 위치 연결 |
| 5. 데이터와 판단 기준 | 입력·출처·관계·단위·분모·기준시각·상태의 의미와 계산/해석 주의점 |
| 6. 확정 사실·가정·미확인 | 확인 사실과 근거, 사용자 정보, 추론·가정, 미확인이 결정에 미치는 영향. 관련 질문은 번호로 연결 |
| 7. 다음 단계 전달 | 설계가 반드시 지켜야 할 조건, 남은 판단과 관련 출처 위치 |

용어는 `용어 | 쉬운 설명 | 이 과제에서 중요한 점` 형식의 표를 기본으로 쓴다. 약어는 확인한 원어를 함께 적고 사전식 정의에서 끝내지 않는다. 예를 들어 과제가 “최신 검사 PASS여도 Hold는 유지”라고 정의했다면 Hold의 설명에 그 판단상의 차이를 연결한다. 이는 예시이며 다른 과제에 같은 규칙을 가정하지 않는다. 용어 관계는 짧은 흐름이나 표로 이해가 더 쉬워질 때만 표현한다.

출처는 관련 설명 가까이에 링크·제공 자료 위치를 붙인다. 확인된 일반 지식과 과제 전용 정의를 구분한다. 필수 요구에는 짧은 항목명이나 필요한 경우 식별자를 붙여 이후 설계·검증에서 같은 요구를 추적할 수 있게 한다. 고정 ID 체계나 긴 요구사항 대장을 강제하지 않는다.

## 현업 챗봇에 확인할 질문과 회신

제공 자료와 기존 회신을 확인한 뒤에도 업무 판단이나 결과 검증에 필요한 사실이 남으면, 분석 문서 끝에 제목 `## 확인이 필요한 부분`을 둔다. 중요한 질문부터 한 번에 기본 최대 5개를 `1.`, `2.` 순서로 적는다. 챗봇이 과제의 어느 용어·상황·판단을 묻는지 알 수 있는 완결된 질문으로 쓴다. 질문 목록에는 사용자가 실제로 전달할 문장만 담는다. 예시 질문, 예상 답, 이미 확인한 사실, 사용자와 설계 단계에서 선택할 사항을 섞지 않는다.

확인된 분석을 먼저 저장하고, 대화에는 문서 링크와 함께 이번에 물을 문장만 같은 번호·문구로 복사 가능한 텍스트 블록 하나에 담는다. 사용자가 허용된 현업 챗봇에 직접 묻고 받은 답을 전달한다. 에이전트가 대신 전송하거나 챗봇의 답을 만들어 채우지 않는다.

회신을 받으면 같은 절에서 원래 질문 번호에 실제 답·근거(사용자가 전달한 회신 및 대조한 자료 위치)·판단이나 검증에 미치는 영향을 기록한다. 답에 따라 바뀐 요구·용어·데이터 기준·설계 인계도 본문에서 함께 고친다. 답이 일부이거나 자료와 충돌하면 확인된 범위와 남은 쟁점을 구분하고, 해결에 필요한 후속 질문만 추린다. 기존 질문 번호는 유지하며 새 질문에는 다음 번호를 붙이고 관련 원번호를 연결한다. 회신을 어느 질문에 연결할지 불명확하면 내용을 임의로 배정하지 말고 사용자에게 확인한다.

새 대화에서 재개할 때도 기존 문서의 질문·회신과 현재 자료를 먼저 읽고 미해결 부분부터 이어간다. 무응답을 근거로 가정을 확정하지 않는다. 업무 판단이나 검증 결과를 바꿀 핵심 기준이 남아 있으면 문서와 대화 모두 분석 진행 중으로 표시하고 확인 가능한 작업만 계속한다. 해당 기준이 자료나 실제 회신으로 해소되고 필수 분석 본문이 갖춰지면 완료한다. 처음부터 확인할 질문이 없으면 빈 질문 절이나 챗봇 문의 절차를 만들지 않고 완료 여부를 판단한다.

## 대화 응답과 전달

완료 응답은 “문제 분석 문서를 작성했습니다”와 실제 문서 링크를 중심으로 짧게 쓴다. 인계에 필요한 한계가 있을 때만 덧붙인다. 긴 분석·용어 표를 대화에 재출력하거나 “원하시면 저장하겠습니다”로 끝내지 않는다. 사용자가 상세 설명을 요청하면 해당 내용을 충분히 설명한다.

작업 ID는 생성하지 않는다. 산출물에는 확인한 원문/입력과 갱신 시각, 남은 질문을 표시한다. 조사 결과가 있다는 이유로 미확인을 확정 처리하거나 솔루션·실행 승인을 만들지 않는다. 다음 단계는 이 분석 본문을 읽어 재사용하며, 이미 이해한 내용을 처음부터 재조사하지 않는다.
