# 검증과 마무리

[승인 기준](approval.md)에 따라 검증 권한과 수정 권한을 구분한다. 검토·검증만 요청받았다면 읽기와 허용된 검사로 결과를 보고하고 코드·설정·기록 파일을 임의로 수정하지 않는다. 검사 중 설치·마이그레이션·외부 쓰기 등 새로운 변경이 필요하면 먼저 확인한다.

검증만 요청받은 기존 프로젝트에 설계·계획 기록이 없다면 현재 요청·코드·확보된 근거로 확인 가능한 범위를 정하고 누락을 밝힌다. 승인·과거 계획을 소급해 만들거나 검증을 위해 전체 설계 절차를 강제하지 않는다. 요구 기준이 불명확해 판정할 수 없는 부분만 확인한다.

1. 기준 버전의 공통 `.skhy/design.md`의 기대 업무 결과·범위·계약과 해당 작업에서 승인된 `execution-plan.md`의 변경·테스트·완료 기준을 실제 코드·`implementation.md`·실행 결과와 함께 대조한다. 기록 문장만으로 구현 여부를 판단하지 않는다. 원래 요구의 누락·해석을 확인해야 할 때는 design의 입력 discovery에서 해당 항목을 확인한다.
2. 변경 위험에 맞춰 핵심 계산·데이터 단위·API 계약·통합·화면 흐름을 검사한다. 정상·경계·실패·빈 데이터·원격 장애 중 관련 경로를 고른다. 실제 프로젝트의 실행 명령·제공 환경을 확인해 수행하며 모의 응답·실제 허용 API 확인·수동 화면 관찰을 구분한다.
   원인 불명·간헐 오류를 점검할 때는 [재현 절차](../../solution-design/references/tests.md)에 따라 허용된 동작과 근거로 원래 증상을 확인한다. 이미 수정된 결과를 검증할 때는 확보한 수정 전 근거와 같은 조건에서 비교하고, 추가 변경이 필요한 재현은 미확인 범위로 보고한다.
3. 실패는 원인을 확인한다. 수정까지 승인된 범위의 결함만 수정·재검증한다. 수정 권한이 없으면 결함·근거·수정안을 보고하고 사용자 확정을 기다린다. 상당한 범위·솔루션·계약 변경은 영향과 수정안을 적절한 설계/계획 검토에 올린다. 검사 후 변경이 있으면 영향을 받는 검사만 갱신한다. 여러 에이전트 결과는 최종 통합 상태에서 확인한다.
4. 최종 status·diff·관련 커밋과 새 파일·지정 제출물을 검토한다. 논리 단위 커밋과 실제 변경의 대응, 기존 사용자 변경 보존, 파일명·경로·내용·저장 상태를 확인한다. `.skhy/` 기록을 지정 제출물로 대신하지 않는다.
5. 파일 작성이 승인된 작업은 [기록 기준](records.md)에 따라 `verification.md`에 솔루션/실행 계획의 승인 버전 참조, 주요 기준별 결과·근거, 실제 검사 명령·시각·종료 결과 또는 수동 동작/관찰, 남은 한계·다음 일을 남긴다. 긴 출력·화면은 필요할 때만 `evidence/`에 보존하고 실패 근거를 지우지 않는다. 인증정보는 가리고 필터 적용을 명시한다.
6. 실제 변경·확인 결과·미실행/실패·남은 제한을 간결히 보고한다. 테스트 통과를 요구 전체 충족으로 일반화하지 않고 다른 세션·호스트의 동작까지 확인했다고 쓰지 않는다. 제출 버튼 조작은 사용자에게 남기며 후속 서술형 단계에서는 답변 생성 등 AI를 사용하지 않는다.
