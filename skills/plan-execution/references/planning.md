# 실행 계획

목적은 솔루션을 실제 코드 작업으로 재해석하고, 이해한 내용과 구체적 실행 계획을 함께 검토받는 것이다. 변경 권한은 [승인 기준](approval.md)을 따른다.

1. 적용 지침·사용자의 최신 정정과 프로젝트 공통 `.skhy/design.md` 또는 대화의 확정 설계안에서 승인 버전·근거를 확인한다. 파일이 없으면 해당 메시지·구획과 승인 내용을 참조하며 파일 존재를 다음 단계의 조건으로 삼지 않는다. 승인되지 않은 제안이나 폐기된 대안을 실행 기준으로 삼지 않는다. 솔루션 이해가 달라졌다면 중요한 차이를 먼저 정리한다. 산출물을 읽은 사실을 설계 스킬 재호출로 대체하지 않는다. 요구 해석 확인이 필요할 때만 design이 참조한 discovery의 해당 항목을 읽는다.
   계획 작성 전에 대상 프로젝트 루트 `AGENTS.md`와 확정된 개발 규칙을 대조한다. 이전 설계에 정책 반영이 빠졌다면 [개발 정책 반영](../../solution-design/references/development-policy.md)만 이어서 수행한다. 같은 규칙이 이미 있으면 그대로 사용한다. 충돌이나 저장 장애·쓰기 제한으로 정책이 미반영된 경우 새 실행 계획의 작성·승인은 보류한다. 기존 계획의 검토만 요청받으면 현재 근거로 의견을 제시하고 파일은 쓰지 않는다.
2. [기록 기준](records.md)에 따라 이번 개별 구현 작업의 기존 ID를 확인하거나 새 작업 ID를 정한다. 공통 설계 중 이번 작업의 범위·제외를 명확히 하고 `.skhy/tasks/<작업-id>/`에서 계획을 관리한다. 실제 기존 폴더·관련 모듈·인터페이스·테스트와 사용자 변경을 읽는다. 현재 구조에서 재사용할 부분, 변경할 파일/책임, 새 경계와 데이터 흐름을 솔루션에 대응시킨다. 조사만을 위해 전 파일·로그를 읽지 않는다.
3. 구현 순서와 의존성, 직접 수행/위임 범위·파일 소유권, 테스트·완료 기준과 필요한 Git 동작을 계획한다. 남은 시간에 맞춰 화면부터 데이터/API까지 연결되는 최소 흐름을 먼저 정하고, 실제 연동을 처음 확인할 시점·최종 통합/제출 확인 여유·시간 부족 시 사용자에게 제안할 축소 순서를 포함한다. 고정 시간표를 강제하지 않는다. 필요한 경우에만 [구조](../../solution-design/references/architecture.md)·[테스트](../../solution-design/references/tests.md)·[Git](../../solution-design/references/git.md)의 해당 기준을 확인한다. 위임이 유리하면 [delegate-work](../../delegate-work/SKILL.md)의 가용 도구·모델·허용 범위를 확인한다.
4. 부모 솔루션의 승인 버전과 파일 경로 또는 대화 근거, 코드 관점의 이해, 변경 범위·순서·담당·검증과 필요한 실행 권한을 함께 제시해 **코드 구현 전에 명시적인 사용자 승인을 받는다.** 설계 내용을 다시 복제하지 말고 실제 구현 결정을 보탠다. 계획 파일 작성도 허용된 경우만 `execution-plan.md`에 초안을 적고, 그렇지 않으면 대화로 제시한 뒤 저장까지 승인된 확정본을 [기록 기준](records.md)에 따라 남긴다. `design.md`의 승인만으로 제품 코드 수정·설치를 시작하지 않는다.
5. 이미 같은 실행 계획에 대한 명시적 승인이 있으면 실제 근거를 연결해 재사용하고 반복해서 묻지 않는다. 승인이 어느 버전에 해당하는지 모호하면 해당 차이만 확인한다. 계획을 바꿀 때는 합의된 Git 정책에 따라 이전 확정본의 커밋을 확인하고 같은 파일을 갱신한다. 승인된 실행 계획이 준비되면 구현 단계로 넘어가 [구현](implementation.md)을 읽는다.

구현 순서의 미세 조정까지 재승인하지 않는다. 핵심 기능·계약·선택 기술·외부 권한 등 합의를 바꾸는 차이만 영향과 변경안을 제시해 확인한다. 계획 파일이 있다는 사실은 승인 근거가 아니다.
