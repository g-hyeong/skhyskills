# 구현

1. [승인 기준](approval.md)에 따라 적용 지침과 `execution-plan.md` 또는 대화에서 확정한 실행 계획의 승인 버전·근거·허용 동작부터 확인한다. 하위 작업은 부모 승인 계획의 경로와 맡은 범위를 참조하며 같은 계획을 복제하거나 재승인받지 않는다. 계획이 참조한 필요한 공통 솔루션 결정과 관련 코드·계약만 이어 읽고 기존 `implementation.md`의 실제 완료 범위부터 재개한다. 앞 단계 스킬을 다시 호출해 같은 산출물을 만들지 않는다. 계획 승인이 없으면 코드 구현을 시작하지 않고 [계획](planning.md)으로 돌아간다.
2. 원인이 불분명하거나 간헐적으로 발생하는 오류는 수정 전에 [테스트의 재현 절차](../../solution-design/references/tests.md)에 따라 허용된 동작으로 원래 증상과 원인 가설을 확인한다. 승인된 범위와 기존 구조에 맞춰 코드·테스트를 변경한다. 핵심 로직·실패 경로를 구현 중 함께 확인하며 불필요한 리팩터링·새 기능·의존성을 추가하지 않는다. 실제 필요한 경우에만 [API](../../solution-design/references/api.md)·[UI](../../solution-design/references/ui.md)·[테스트](../../solution-design/references/tests.md)·[구조](../../solution-design/references/architecture.md) 참조를 선택한다.
3. 위임 시 [delegate-work](../../delegate-work/SKILL.md)에 따라 최신 승인 조건과 변경 범위를 전달한다. 파일별 작성자는 하나, 공유 작업 트리의 Git 변경 담당자도 하나로 정한다. 다른 사람의 변경을 되돌리거나 스테이징·커밋하지 않는다.
4. 합의된 Git 정책과 허용 범위에서 [Git 기준](../../solution-design/references/git.md)에 따라 논리 단위별 관련 코드·테스트를 커밋한다. 커밋하지 말라는 요청이 있으면 따르고 실제 미커밋 상태를 보고한다. 커밋 형식을 이유로 새 브랜치·PR·외부 게시를 자동으로 만들지 않는다.
5. [기록 기준](records.md)에 따라 `implementation.md`에 승인 계획 참조, 실제 변경과 이유, 수행한 검사·커밋 근거, 차이·남은 일만 남긴다. 계획·의도와 실제 구현 결과를 구분한다. 같은 오류가 반복되면 입력·범위·방법을 먼저 확인하고 맹목적으로 재시도하지 않는다.
6. 승인된 변경 범위 안의 결함과 구현 조정만 수정하고 해당 부분을 재검증한다. 범위 밖의 개선은 발견 사항으로 제안하며 먼저 실행하지 않는다. 상당한 범위·솔루션·계약 변화가 필요하면 변경 영향을 정리해 적절한 설계/계획 검토로 돌아간다. 완료한 변경은 [검증](verification.md)에서 최종 통합 결과로 확인한다.
