# 사용자 확정 범위와 승인

요청된 스킬의 기본 산출물 작성과 제품 변경 권한을 구분한다. “이 과제를 분석해 줘”처럼 task-discovery를 수행하는 요청에는 `.skhy/discovery.md` 작성·갱신이 포함된다. solution-design 요청에는 질문·피드백으로 설계를 합의한 뒤 `.skhy/design.md`를 작성·갱신하고 대상 프로젝트 루트 `AGENTS.md`에 [확정 개발 정책을 반영](../../solution-design/references/development-policy.md)하는 것까지 포함된다. 실행 계획 작성으로 재개할 때도 이미 합의한 정책의 누락만 보완할 수 있다. 이 범위의 저장은 재승인을 요구하지 않는다. 사용자가 “파일은 만들지 마”, “대화로만”처럼 명시적으로 제한한 경우는 따른다.

제품 코드·설정 수정·설치·Git 변경·외부 동작은 확정된 별도 실행 범위에서만 진행한다. 일반 질의나 기존 코드/문서의 검토·검증 요청은 해당 대상의 수정 승인이 아니다. 침묵, 도구의 기본 선택, 다른 에이전트의 판단도 승인이 아니다.

- 현재 사용자 요청에 구체적인 변경과 실행 지시가 있으면 그 범위의 승인으로 재사용한다. 같은 결정을 다시 묻지 않는다. 솔루션 방향에 대한 동의만으로 구체적 구현 계획이 승인되었다고 간주하지 않는다.
- 승인할 안에는 바꿀 대상·범위·이유·검증 방법과 필요한 설치/Git/외부 동작을 한 번에 제시한다. 해당되지 않는 항목으로 체크리스트를 늘리지 않는다. 중요한 선택은 사용자에게 남기고 애매한 “알아서”를 범위 확대 근거로 쓰지 않는다.
- 확인이 필요하면 현재 호스트의 질문 도구를 우선 사용한다. 추천안과 대안 또는 보류를 짧게 제시하고 **실제 사용자 답을 받은 뒤** 실행한다. 질문 도구가 없으면 대화로 묻는다. 타임아웃·무응답은 승인으로 처리하지 않으며, 답을 기다리는 동안은 이미 허용된 독립 작업만 한다.
- 위 두 스킬의 산출물은 요청 자체에 포함된 결과다. 산출물 저장을 이유로 제품 파일·설치·실행 계획 승인까지 허용됐다고 확대하지 않는다. 그 밖의 단순 질문·검토에서는 요청하지 않은 기록을 만들거나 검토 대상을 수정하지 않는다. 파일을 쓰지 말라는 명시적 요청이나 실제 저장 장애가 있을 때만 대화로 전달하고 그 한계를 밝힌다.
- 작은 버그라도 수정 권한 밖이면 근거와 수정안을 보고한다. 승인된 구현·테스트 범위 안의 수정은 진행할 수 있지만, 사용자 동작·계약·기술·의존성·권한·비용의 중요한 변경은 먼저 확정받는다. 시간 부족이나 품질 개선을 이유로 기능을 임의로 빼거나 추가하지 않는다.
- 하위 작업자는 부모가 전달한 **실제 사용자 승인 계획의 해당 범위**만 이어받는다. 부모의 위임 자체가 새 권한은 아니다. 자식은 승인 범위를 확대하거나 승인 기록을 만들어내지 않는다.

승인은 대상 계획의 개정과 연결한다. 실제 사용자 답과 승인 범위를 기록하되 대화를 통째로 복사하지 않는다. 최신 계획 파일과 로컬 Git 이력의 연결·인계는 [기록 기준](records.md)을 따른다.
